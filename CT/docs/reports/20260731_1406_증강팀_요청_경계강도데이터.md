# [요청] 사양보다 약한 강도의 CT FAIL 추가 생성

**보내는 곳**: CT 품질 게이트 분류기 담당
**작성**: 2026-07-31 · 개정 14:35
**기준**: 데이터 증강 계획서 v1.9 / 데이터셋 `quality_fail_40k_v1.8_20260730`

> **요청 범위는 증강 방식(파라미터 값)뿐입니다.**
> 출력 형식·폴더 구조·JSON 스키마·ID 발급 규칙은 **v1.9 그대로 두시면 됩니다.**
> 변경 요청 없습니다.

---

## 요청 한 줄

**사양 범위보다 "약한" 강도의 CT FAIL을 약 950장 추가 생성해 주시기 바랍니다.**
증강 코드와 원본 데이터가 이미 그쪽에 있으므로 **파라미터 값만 바꿔 1회 실행**하면 되는 작업입니다.

---

## 1. 배경

### 먼저, 받은 데이터는 잘 만들어졌습니다

저희가 검증한 결과 아래가 모두 깨끗했습니다.

| 점검 항목 | 결과 |
|---|---|
| 라벨 정확성 (JSON · pass/fail 폴더 · 증강이력 3중 대조) | **불일치 0건** |
| 케이스별 수량 (사양 대비) | 5종 **전부 정확히 일치** |
| PASS/FAIL의 JPEG 저장 설정 차이 | **없음** (q90 동일) |
| 종횡비로 FAIL을 구별할 수 있는지 | **불가** (분포 동일 — 의도대로) |
| 증강 처리 흔적으로 분류기가 속는지 | **속지 않음** |

마지막 항목은 특히 신경 써서 확인했습니다. 픽셀을 **전혀 바꾸지 않고** 동일 설정으로
JPEG만 다시 저장한 이미지를 분류기에 넣었더니 점수가 원본과 같았습니다(차이 +0.02).
**증강 파이프라인을 거쳤다는 흔적만으로 FAIL 판정이 나오지 않습니다.**

### 그런데 성능을 측정할 수가 없습니다

분류기가 held-out 셀에서 recall 0.98을 냈는데 **이 숫자를 신뢰할 수 없습니다.**
데이터에 **애매한 사진이 하나도 없기 때문**입니다.

강도를 직접 바꿔가며 분류기 반응을 재봤습니다.

| | 분류기가 반응하기 시작하는 지점 | **v1.9 사양 범위** |
|---|---|---|
| 저신호 노이즈 | `photon_scale` 약 **3,000** | **10 ~ 40** |
| 이중 영상 | `offset_final_512_px` 약 **2px** | **18 ~ 28px** |

**사양 범위 전체가 분류기 감지 문턱보다 수십~수백 배 심한 쪽에 있습니다.**

실제로 `ct_low_signal_noise`에서 photon을 39.9 → 10.3으로 **4배** 바꿔도
분류기 점수 여유가 10.53 → 10.50으로 사실상 그대로였습니다.

> 비유하자면, 화재감지기를 **큰 화재 사진으로만** 시험한 셈입니다.
> 100점이 나와도 **촛불에 반응하는지는 알 수 없습니다.**

이건 증강이 잘못됐다는 뜻이 **아닙니다.** v1.9의 자동 통과 조건(§4.7)이
"확실히 실패로 보이는" 결과만 통과시키도록 설계돼 있으니 당연한 결과입니다.
다만 **그 데이터로는 분류기의 실제 검출 문턱을 잴 수 없습니다.**

### 저희가 직접 만들어 봤지만 한계가 있습니다

위 문턱 숫자(3,000 / 2px)는 저희 근사 구현으로 낸 값입니다.
`ct_low_signal_noise`는 v1.9 §2.2.4의 **4단계 중 1단계(Poisson)만** 구현했고
`signal_to_transmission`, `read_noise`, `low_contrast_attenuation`은 생략했습니다.

그 탓에 극단 강도에서 값이 뒤집히는 현상도 나왔습니다(photon=10이 photon=25보다 낮게 측정).
**정확한 문턱을 알려면 실제 생성 코드로 만든 데이터가 필요합니다.**

## 2. 요청 사항

### 2.1 파라미터 값

각 케이스마다 **사양 범위 바깥(= 더 약한 쪽)** 의 고정값으로 생성해 주시기 바랍니다.
**나머지 파라미터는 v1.9 사양 그대로** 두시고, 아래 하나만 고정해 주십시오.

| 케이스 | 고정할 파라미터 | **요청 값** | (참고) v1.9 사양 |
|---|---|---|---|
| `ct_low_signal_noise` | `photon_scale` | **3000 / 1000 / 300 / 100** | 10 ~ 40 |
| `ct_acquisition_motion` | `offset_final_512_px` | **2 / 5 / 10 / 14** | 18 ~ 28 |
| `ct_insufficient_projection_sampling` | `retained_ratio` | **0.55 / 0.65 / 0.75 / 0.85** | 0.20 ~ 0.45 |
| `ct_cell_alignment_failure` | `retained_outline_ratio` | **0.92 / 0.95 / 0.97** | 0.50 ~ 0.90 |
| `ct_beam_hardening_metal_streak` | `streak_count` | **6 / 12 / 18** | 24 ~ 72 |

**수량**: 각 지점당 **50장** → 합계 **950장**

### 2.2 ⚠️ 자동 통과 조건(gate)을 꺼 주십시오

**이 항목만은 반드시 필요합니다.**

v1.9 §4.7의 gate가 "약한" 결과를 실패로 판정해 reserve source로 교체해 버립니다.
**이 요청은 일부러 gate 미달을 만드는 것**이므로, gate를 끄지 않으면
생성이 진행되지 않고 `generation_errors.csv`만 쌓입니다.

### 2.3 (가능하면) 원본 셀 15개로 제한

분류기 학습에 사용한 셀이 섞이면 측정이 부정확해집니다.
가능하면 아래 **원본 battery_id 15개**에서만 뽑아 주시면 좋겠습니다.

```
102, 103, 108, 114, 120, 122, 125, 134, 135, 140, 141, 143, 144, 146, 147
```

**어려우면 그냥 기본 로직대로 뽑으셔도 됩니다.**
공개 `augmentation_json`의 `group_key`에 원본 battery_id가 들어 있어
저희 쪽에서 걸러낼 수 있습니다(47개 셀 전부 1:1 역산 확인 완료).
다만 그 경우 쓸 수 있는 장수가 1/3 정도로 줄어드니, 가능하면 제한 부탁드립니다.

## 3. 출력 형식 — 변경 요청 없음

**v1.9 표준 형식 그대로** 내주시면 됩니다.

- 폴더 구조, 파일명 규칙, ID 발급 범위 — 기존 그대로
- 라벨 JSON의 `quality_class: "fail"` — **그대로 두셔도 됩니다**
- `augmentation.json`의 파라미터·`severity`·`group_key` 기록 — 기존 그대로

저희는 이 데이터를 **강도별 반응 측정에만** 쓰므로 `quality_class` 값은 사용하지 않고,
`augmentation.json`에 기록된 **실제 파라미터 값**만 읽습니다.

기존 데이터셋과 섞이지 않도록 **별도 출력 폴더**로만 내주시면 충분합니다.

## 4. 용도

**평가 전용입니다. 분류기 학습에 넣지 않습니다.**

"우리 게이트는 어느 강도 이상을 걸러내는가"를 확정해 **운영 사양 문장**을 쓰는 데 씁니다.

현재는 *"recall 0.98"* 밖에 말할 수 없습니다.
이 데이터를 받으면 *"photon ○○ 이하, 흔들림 ○○px 이상을 걸러낸다"* 고 쓸 수 있고,
그래야 공정 쪽에서 재촬영 기준을 정할 수 있습니다.
